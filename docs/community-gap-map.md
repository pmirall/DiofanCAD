# DiofanCAD — Community Gap Map

## Purpose

Turn community feedback into evidence-backed product requirements without letting popularity alone become the specification.

## V7 process

```text
signal
 ↓
reproduce
 ↓
classify
 ↓
impact/frequency
 ↓
requirement
 ↓
benchmark
 ↓
Gauntlet
 ↓
community validation
```

## Gap record

Each gap should contain:

```text
ID
source / signal
user problem
workflow
frequency
impact
current workaround
reproduction
failure taxonomy
candidate requirement
benchmark link
priority
status
affected upstream subsystem
```

## Initial categories

| Category | Initial state | Evidence required |
|---|---|---|
| Sketcher | TO VALIDATE | reproduced workflow data |
| Part Design / topology resilience | TO VALIDATE | change-challenge cases |
| Assembly | TO VALIDATE | assembly workflow studies |
| TechDraw / release | TO VALIDATE | drawing/release cases |
| CAM | TO VALIDATE | manufacturing workflow evidence |
| FEM | TO VALIDATE | study preparation evidence |
| ECAD ↔ MCAD | TO VALIDATE | integration cases |
| API / automation | TO VALIDATE | automation use cases |
| Performance / scale | TO VALIDATE | benchmark evidence |
| Data ownership / interoperability | TO VALIDATE | compatibility tests |

## Anti-bias rule

A frequently requested feature does not automatically become a roadmap commitment. It becomes a candidate requirement only after reproduction, impact assessment, and a measurable bar.
